EVM Gas, Fees & Tokens — A Complete Guide

This guide provides a thorough explanation of gas fees, units, wei, native tokens, ERC-20 tokens, and their relationships across EVM-compatible chains. It is aimed at developers and deployers who need a precise mental model of how these concepts interrelate and who may encounter confusion between gas units, wei, and token amounts.

Whether you are debugging a failed transaction, optimizing a smart contract for gas efficiency, or building cross-chain applications with LayerZero, this guide covers the full spectrum — from foundational concepts through the latest 2025 protocol upgrades.

1. Native Tokens vs ERC-20 Tokens

1.1 Native Tokens

Every EVM-compatible blockchain has exactly one native token. This is the token built into the protocol itself — it is not a smart contract and does not have a contract address.

Chain Native Token
Ethereum ETH
BSC BNB
Polygon POL (formerly MATIC)
Avalanche AVAX
Arbitrum ETH
Base ETH
Fantom FTM
Scroll ETH
zkSync Era ETH
Linea ETH

Key characteristics of native tokens:

  • Protocol-level existence. The native token is intrinsic to the chain. Every account has a balance field that holds its native token amount, denominated in the smallest unit (wei for Ethereum, or the chain’s equivalent).
  • Gas payment. The native token is the only token that can be used to pay transaction fees (gas). You cannot pay gas with USDT, WETH, or any other ERC-20 token directly. (Note: Account Abstraction via ERC-4337 changes this — see Section 8.2.)
  • Simple transfers. Sending native tokens requires only setting the value field of a transaction. No smart contract interaction is needed.
  • No contract address. Because native tokens exist at the protocol level, they do not have a contract address. Tools and protocols sometimes use a sentinel address like 0xEeeeeEeeeEeEeeEeEeEeeEEEeeeeEeeeeeeeEEeE or address(0) to represent the native token.

Pro Tip: When writing multi-chain code, never assume the native token symbol. Use chain config to resolve it. On Arbitrum and Base, the native token is ETH even though they are L2s — the protocol-level balance tracks bridged ETH.

1.2 ERC-20 Tokens

ERC-20 tokens are smart contract-based tokens that follow the ERC-20 standard. Unlike native tokens, each ERC-20 token is a separate deployed smart contract with its own address on the blockchain.

Key characteristics:

  • Contract-based. The token’s state (balances, allowances) is stored inside the smart contract, not in the protocol’s account state. The contract maintains an internal mapping of address => uint256 for balances.
  • Transfers require contract calls. To send ERC-20 tokens, you must call the token contract’s transfer(to, amount) or transferFrom(from, to, amount) function. This is a transaction that executes code, which means it costs more gas than a simple native token transfer.
  • Approval mechanism. Before a third party (like a DEX router) can move your tokens, you must first call approve(spender, amount) on the token contract. This is a separate transaction that also costs gas.
  • Gas is still paid in native tokens. Even though you are transferring ERC-20 tokens, the transaction fee is always paid in the chain’s native token.
  • Common examples: USDT, USDC, DAI, WETH, WBNB, UNI, CAKE, LINK, AAVE.

Warning: Some ERC-20 tokens implement non-standard behavior — transfer fees (tax tokens), rebasing balances, or blacklists. Always check the token contract before integrating. The transfer() return value is not always checked, leading to silent failures with tokens like USDT (which does not return bool on older deployments).

1.3 Wrapped Native Tokens (WETH, WBNB)

Wrapped native tokens are ERC-20 representations of a chain’s native token, backed 1:1.

Chain Native Wrapped ERC-20
Ethereum ETH WETH
BSC BNB WBNB
Polygon POL WPOL
Avalanche AVAX WAVAX
Fantom FTM WFTM

Why wrapped tokens exist:

Native tokens do not conform to the ERC-20 interface. They lack transfer(), approve(), balanceOf(), and the other functions that DeFi protocols rely on. Rather than building special cases for native tokens into every protocol, the ecosystem created wrapper contracts that give native tokens an ERC-20 interface.

How wrapping works:

  1. Wrap (deposit): You send native tokens (e.g., 1 ETH) to the WETH contract. The contract holds the native tokens and mints 1 WETH (ERC-20) to your address.
  2. Unwrap (withdraw): You call withdraw(amount) on the WETH contract. It burns the WETH and sends the equivalent native tokens back to you.

The wrapper contract always holds exactly as many native tokens as there are wrapped tokens in circulation, maintaining the 1:1 peg.

Pro Tip: The canonical WETH contract (deployed at 0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2 on Ethereum mainnet) is one of the most battle-tested contracts in DeFi. It has been in use since 2017 and holds billions in TVL. The interface is intentionally minimal — deposit(), withdraw(), and the standard ERC-20 functions.

2. Understanding Wei — The Smallest Unit

2.1 The Denomination System

Just as 1 dollar = 100 cents, 1 ETH = 10^18 wei. However, unlike the dollar which has only 2 decimal places, ETH has 18 decimal places, allowing for extremely precise fractional amounts.

The complete denomination table for Ethereum (and most EVM chains):

Unit Wei Value Scientific Notation Decimal Places from ETH
wei 1 10^0 18
kwei (babbage) 1,000 10^3 15
mwei (lovelace) 1,000,000 10^6 12
gwei (shannon) 1,000,000,000 10^9 9
szabo 1,000,000,000,000 10^12 6
finney 1,000,000,000,000,000 10^15 3
ether 1,000,000,000,000,000,000 10^18 0

In practice, only three of these are commonly used:

  • wei — the base unit, used internally by the EVM for all arithmetic
  • gwei — used to express gas prices (e.g., "gas price is 5 gwei")
  • ether — the human-readable unit (e.g., "I sent 1.5 ETH")

Analogy: Wei is to ETH what cents are to dollars, but with 18 decimal places instead of 2. If dollars worked like ETH, one dollar would equal 1,000,000,000,000,000,000 "cents."

2.2 Why Wei Exists

The EVM is a pure integer machine. It has no floating-point arithmetic. Every value — balances, transfer amounts, gas prices — is a 256-bit unsigned integer. There is no concept of 0.5 ETH inside the EVM; there is only 500000000000000000 wei.

This design choice was deliberate:

  • Floating-point is non-deterministic. Different hardware and compilers can produce slightly different results for the same floating-point calculation. In a consensus system where every node must arrive at exactly the same result, this is unacceptable.
  • Integer arithmetic is exact. 1 + 1 = 2, always, on every machine, in every implementation.
  • 18 decimals provide sufficient precision. With 10^18 subdivisions of one ETH, you can represent amounts as small as 0.000000000000000001 ETH, which is more than sufficient for any practical use case including micro-transactions.
  • All values in the EVM are stored and computed in wei. When your wallet displays "1.5 ETH," it is reading the value 1500000000000000000 from the blockchain and dividing by 10^18 for display.

Pro Tip: The EVM’s 256-bit integer size means the maximum possible value is 2^256 - 1 (approximately 1.16 x 10^77). Even with 18 decimals, this allows representing a truly astronomical number of ETH — far exceeding the total supply. You will never overflow a uint256 with normal token arithmetic, but you can overflow with multiplication before division. Always multiply before dividing to preserve precision, and use libraries like OpenZeppelin’s Math for safe operations.

2.4 ERC-20 Decimals Are NOT Always 18

A critical source of bugs: not all tokens use 18 decimals. Each ERC-20 token defines its own decimals() value, and you must use the correct one when converting between human-readable amounts and raw integer values.

Token Decimals 1 Token in Smallest Unit Notes
ETH (native) 18 1,000,000,000,000,000,000 Protocol-level
BNB (native) 18 1,000,000,000,000,000,000 Protocol-level
WETH 18 1,000,000,000,000,000,000 Matches native ETH
WBNB 18 1,000,000,000,000,000,000 Matches native BNB
DAI 18 1,000,000,000,000,000,000
USDT 6 1,000,000 Common source of bugs
USDC 6 1,000,000 Common source of bugs
WBTC 8 100,000,000 Matches Bitcoin’s 8 decimals
BTC.b 8 100,000,000 Avalanche bridged Bitcoin
GUSD 2 100 Gemini USD — only 2 decimals

The danger of assuming 18 decimals:

If you use parseEther('100') to represent 100 USDT, you get 100000000000000000000 (100 * 10^18). But USDT only has 6 decimals, so the correct raw value for 100 USDT is 100000000 (100 * 10^6). Using the wrong value would attempt to transfer an astronomically larger amount and would either fail or cause severe loss.

Always use the token’s actual decimals:

Warning: Some malicious or misconfigured tokens return unexpected values for decimals() — including 0 or values greater than 18. Always validate that decimals is within a reasonable range (0-18) before using it in calculations. Tokens with 0 decimals do exist legitimately (e.g., some NFT-like tokens), but they require special handling in UIs.

3. Gas — The Computation Unit

3.1 What Is Gas?

Gas is an abstract unit of measurement that quantifies the computational effort required to execute operations on the EVM. It is critical to understand what gas is and what it is not:

  • Gas is NOT a token.
  • Gas is NOT a currency.
  • Gas is NOT a denomination of ETH or any native token.
  • Gas is NOT measured in wei or gwei.
  • Gas IS a dimensionless unit, like "calories" or "CPU cycles."

Every operation that the EVM can perform (called an "opcode") has a fixed gas cost assigned to it by the protocol. More complex operations cost more gas. Storage operations are especially expensive because they permanently modify the blockchain state.

When you submit a transaction, the total gas consumed is the sum of gas costs for every opcode executed during that transaction’s processing.

3.2 Gas Costs by Operation

The following table shows gas costs for common EVM operations. These costs are defined in the Ethereum Yellow Paper and apply to all EVM-compatible chains (though some chains may modify specific costs).

Why storage is so expensive: Writing to storage (SSTORE) modifies the global blockchain state that every full node must store forever. The high gas cost reflects this permanent burden on the network. This is also why gas optimization in Solidity focuses heavily on minimizing storage writes.

Pro Tip: Since EIP-2929 (Berlin upgrade), the EVM distinguishes between "cold" and "warm" storage accesses. The first access to any storage slot or address within a transaction costs the full "cold" price. Subsequent accesses within the same transaction cost the reduced "warm" price. This is why you see gas costs drop dramatically for repeated reads of the same variable. Knowing this, you can restructure code to ensure expensive state is accessed early and cached.

3.3 Gas Limit vs Gas Used

Every transaction specifies a gas limit — the maximum amount of gas the sender is willing to consume. This is distinct from the gas that is actually used.

  • Gas Limit (gas budget): Set by the sender before submitting the transaction. This is a safety cap. The transaction will never consume more gas than this limit.
  • Gas Used (actual consumption): The amount of gas actually consumed during execution. Determined after the transaction runs.

Three scenarios:

Scenario What Happens Cost
Gas Used < Gas Limit Transaction succeeds, unused gas is refunded Pay for Gas Used only
Gas Used = Gas Limit Transaction succeeds, no refund Pay for Gas Limit
Gas Used > Gas Limit (would exceed) Transaction reverts (all state changes rolled back) All gas is consumed — no refund

3.4 Why Gas Exists

Gas solves several fundamental problems in a decentralized computation network:

  1. The Halting Problem. The EVM is Turing-complete, meaning it can execute arbitrary programs. A Turing-complete system cannot, in general, determine whether a program will terminate. Without gas limits, a single infinite loop could cause every node to compute forever, halting the entire network. Gas ensures every computation has a finite bound.

  2. Denial-of-service prevention. Without cost, an attacker could flood the network with computationally expensive transactions for free. Gas makes attacks economically prohibitive.

  3. Resource pricing. Different operations consume different network resources. A simple addition uses minimal CPU, while a storage write creates permanent state. Gas prices reflect these relative costs, ensuring fair resource allocation.

  4. Block space market. Blocks have a gas limit (e.g., 30 million gas on Ethereum, increased to 36 million post-Pectra). When demand exceeds supply, users compete by offering higher gas prices. This creates an efficient market for block inclusion.

  5. Incentive alignment. Validators/miners receive gas fees as compensation for processing transactions and maintaining the network. Gas aligns the incentives of users (who want transactions processed) with validators (who provide computation).

4. Transaction Fees — Putting It All Together

4.1 Legacy Fee Model (Pre-EIP-1559)

Before the London upgrade (August 2021 for Ethereum), all EVM chains used a simple auction model:

  • Gas Price is set by the sender in gwei (or wei). Higher gas price = higher priority.
  • Miners include transactions with the highest gas prices first.
  • The entire fee goes to the miner.

BSC and several other chains still use this model or a close variant of it.

4.2 EIP-1559 Fee Model (Ethereum, post-London upgrade)

EIP-1559, activated on Ethereum in August 2021 and since adopted by many chains, fundamentally changed fee mechanics:

Components:

Component Set By Description
Base Fee Protocol (algorithmic) Adjusts dynamically based on block utilization. If the previous block was more than 50% full, the base fee increases (up to 12.5% per block). If less than 50% full, it decreases. This fee is burned — permanently removed from the ETH supply.
Priority Fee (Tip) User An optional tip paid directly to the validator. Incentivizes validators to include your transaction. Higher tip = faster inclusion.
Max Fee Per Gas User The absolute maximum total fee per gas unit you are willing to pay. Acts as a safety cap. Must be >= Base Fee + Priority Fee.

How it works step by step:

  1. You submit a transaction with maxFeePerGas and maxPriorityFeePerGas.
  2. The protocol determines the current baseFee from the parent block.
  3. The effective gas price = min(maxFeePerGas, baseFee + maxPriorityFeePerGas).
  4. You are charged: gasUsed x effectiveGasPrice.
  5. Of that charge:
    • gasUsed x baseFee is burned (destroyed).
    • gasUsed x (effectiveGasPrice - baseFee) goes to the validator as a tip.
  6. Any excess reservation (gasLimit x maxFeePerGas - gasUsed x effectiveGasPrice) is refunded to you.

Why EIP-1559 matters:

  • Predictable fees. The base fee adjusts smoothly, making fees more predictable than the volatile auction model.
  • Deflationary pressure. Burning the base fee reduces ETH supply over time, potentially making ETH deflationary during high network usage.
  • Reduced overpayment. Under the legacy model, users often overpaid. With EIP-1559, you only pay the effective gas price, and the excess is refunded.

4.3 BSC Fee Model

BNB Smart Chain uses a simplified fee model that is closer to the legacy model:

Key differences from Ethereum:

  • Much lower gas prices: Typical gas prices on BSC are 3-5 gwei, compared to 20-100+ gwei on Ethereum.
  • Lower token price: BNB is typically cheaper than ETH, further reducing USD costs.
  • Faster blocks: BSC produces blocks every 3 seconds (vs. 12 seconds for Ethereum), providing more total block space.
  • No EIP-1559 burn mechanism: BSC has its own burn mechanism (quarterly BNB burns) but does not burn gas fees per-transaction in the same way.

6. LayerZero Cross-Chain Gas — Enforced Options Context

6.1 Why Cross-Chain Needs Gas Limits

When a cross-chain message is sent via LayerZero (e.g., using NativeOFT to bridge tokens), code must execute on both the source chain and the destination chain:

  • Source chain: The user submits a transaction that calls the OFT contract. The user pays source chain gas directly, just like any normal transaction.
  • Destination chain: A LayerZero Executor picks up the message and submits a transaction on the destination chain. But the user is not on the destination chain — so who pays for the destination gas?

The answer: the user pre-pays for destination gas on the source chain. The LayerZero fee (paid in the source chain’s native token as msg.value) includes the estimated cost of destination execution.

setEnforcedOptions is the mechanism by which the OFT contract specifies the minimum gas budget that the Executor must allocate for destination-side execution. This ensures that:

  1. The destination transaction has enough gas to complete successfully.
  2. The user is charged appropriately on the source chain.
  3. The Executor does not under-provision gas and cause the destination transaction to fail.

Why two separate gas limits?

LayerZero V2 separates lzReceive and lzCompose because they are two distinct execution phases:

  1. lzReceive: Called by the Endpoint when the message arrives. Handles the core OFT logic (crediting tokens).
  2. lzCompose: Called as a follow-up if the message contains a composed payload. Handles additional logic (like a DEX swap).

If lzCompose fails (e.g., a swap reverts due to slippage), the tokens credited in lzReceive are still safe — they are not lost. This separation provides fault isolation.

8. Modern Gas Landscape (2025)

The Ethereum ecosystem has undergone dramatic changes in gas mechanics since the original EIP-1559 upgrade. This section covers the most impactful developments that every EVM developer should understand.

8.1 EIP-4844: Proto-Danksharding and Blob Transactions

EIP-4844, activated with the Dencun upgrade in March 2024, introduced a new transaction type (Type 3) that carries blobs — large binary data objects intended for Layer 2 rollup data.

What changed:

Before EIP-4844, L2 rollups posted their transaction data as calldata in regular L1 transactions. At 16 gas per non-zero byte, this was the dominant cost for L2 users. EIP-4844 introduced a separate "blob gas" market with its own pricing:

Aspect Calldata (pre-4844) Blob Data (post-4844)
Cost per byte 16 gas (non-zero) ~1 gas equivalent
Stored in Ethereum state (forever) Blob space (pruned after ~18 days)
Target per block N/A 3 blobs (384 KB)
Max per block Block gas limit 6 blobs (768 KB)
Fee market Shared with execution gas Separate blob fee market
Price mechanism EIP-1559 base fee Separate EIP-1559-style base fee

Impact on L2 costs:

The effect was dramatic. L2 transaction costs dropped by 10-100x overnight. Base, Optimism, and Arbitrum all saw sub-cent transaction fees become the norm rather than the exception.

Pro Tip: Blob data is not accessible from within the EVM. Smart contracts cannot read blob contents — they can only verify blob commitments via the BLOBHASH opcode and the point evaluation precompile. This is by design: blobs are for data availability, not execution.

8.2 Account Abstraction (ERC-4337)

ERC-4337, which reached widespread adoption in 2024-2025, fundamentally changes who can pay for gas and how.

The problem ERC-4337 solves:

Traditionally, every transaction must be sent from an EOA (Externally Owned Account) that holds enough native token to pay gas. This creates a terrible onboarding experience: new users must acquire ETH before they can do anything, even if they already hold ERC-20 tokens.

How it works:

Instead of regular transactions, users create UserOperations — intent objects that describe what they want to do. These UserOps are sent to a separate mempool, picked up by Bundlers, and submitted on-chain to the EntryPoint contract.

The key innovation is the Paymaster — a contract that can sponsor gas fees on behalf of users:

Component Role
UserOperation Describes the action (like a transaction, but more flexible)
Smart Account The user’s on-chain wallet (a contract, not an EOA)
Bundler Collects UserOps and submits them as a regular transaction
EntryPoint Singleton contract that validates and executes UserOps
Paymaster Optional — pays gas fees on behalf of the user

Gas implications:

The overhead is real but decreasing with batching optimizations. The tradeoff is worth it for the UX improvements:

Warning: ERC-4337 UserOperations have a different gas model than regular transactions. They use verificationGasLimit, callGasLimit, and preVerificationGas instead of a single gasLimit. Incorrectly estimating any of these will cause the UserOp to fail. Always use the bundler’s eth_estimateUserOperationGas RPC method rather than manual estimation.

8.3 The Pectra Upgrade

The Pectra upgrade (Prague + Electra), activated on Ethereum mainnet in 2025, brought several gas-relevant changes:

Key changes:

  1. Increased block gas limit. The target block gas limit increased from 30 million to 36 million gas, providing approximately 20% more throughput.

  2. Blob count increase. The target number of blobs per block increased from 3 to 6, and the maximum from 6 to 9. This further reduced L2 data posting costs.

  3. EIP-7702 activation. Allows EOAs to temporarily delegate to smart contract code (see next section).

  4. EIP-2537: BLS12-381 precompile. Adds native BLS signature verification, reducing gas costs for operations that previously required expensive EVM computation.

  5. EIP-7685: General-purpose execution layer requests. Standardizes how the execution layer communicates with the consensus layer.

Pro Tip: The increased block gas limit means the theoretical maximum gas refund also increased. If you are deploying large contracts near the old limit, Pectra may have solved your deployment size concerns. However, the contract code size limit (24,576 bytes per EIP-170) remains unchanged.

8.4 EIP-7702: Set EOA Account Code

EIP-7702, activated with Pectra, is one of the most impactful gas-related changes for user experience. It allows an EOA to set its account code to point to a smart contract implementation for the duration of a single transaction.

What this means:

An EOA can temporarily "become" a smart contract wallet, gaining capabilities like:

  • Batched transactions — approve and swap in a single transaction
  • Gas sponsorship — another account can pay for the transaction
  • Custom validation — use different signature schemes

Gas implications:

Operation Before EIP-7702 With EIP-7702
Approve + Swap 2 TXs (~196,000 gas) 1 TX (~165,000 gas)
Approve + Transfer + Revoke 3 TXs (~133,000 gas) 1 TX (~90,000 gas)
Multi-token operations N separate TXs 1 batched TX

The gas savings come from eliminating redundant 21,000-gas base costs for multiple transactions and from shared storage access warmth within a single transaction.

Warning: EIP-7702 delegations are per-transaction. The EOA reverts to its normal state after the transaction completes. This is different from ERC-4337 smart accounts, which are permanently smart contracts. The two approaches serve different use cases and can coexist.

8.5 Access Lists (EIP-2930)

EIP-2930, introduced with the Berlin upgrade in 2021, added Type 1 transactions with access lists — a pre-declared set of addresses and storage keys the transaction will access.

Why access lists save gas:

Since EIP-2929 (same upgrade), the first access to any address or storage slot costs extra ("cold access premium"). By pre-declaring which addresses and slots your transaction will touch, you pay a discounted rate upfront instead of the full cold-access penalty during execution:

Access Type Without Access List With Access List
Cold address access 2,600 gas (during execution) 2,400 gas (pre-paid) — saves 200
Cold storage slot access 2,100 gas (during execution) 1,900 gas (pre-paid) — saves 200
Warm access (subsequent) 100 gas 100 gas (same)

When to use access lists:

Access lists are most beneficial for transactions that touch many different contracts and storage slots. A simple token transfer rarely benefits, but a complex DeFi interaction involving multiple protocols can save 5-10% on gas.

Pro Tip: Most wallets and RPC providers now automatically generate access lists when beneficial. You generally do not need to manage this manually. However, if you are building a custom transaction submission pipeline (e.g., for MEV or specialized protocols), explicit access lists can give you an edge.

8.6 Flashbots, MEV, and Gas

MEV (Maximal Extractable Value) is the profit that block builders/validators can extract by reordering, inserting, or censoring transactions within a block. MEV has a profound effect on gas dynamics.

How MEV affects gas:

  1. Priority gas auctions (PGA). Bots competing for MEV opportunities (arbitrage, liquidations, sandwich attacks) bid up gas prices, inflating fees for everyone.

  2. Flashbots and the builder API. Flashbots created a private transaction pool where users can submit transaction bundles directly to block builders, bypassing the public mempool. This:

    • Reduces failed transactions — bundles are atomic (all-or-nothing)
    • Eliminates frontrunning — transactions are not visible in the public mempool
    • Stabilizes gas prices — MEV competition moves off-chain

  3. Builder separation (PBS). Post-Merge Ethereum separates block building from block proposing. Builders compete to construct the most profitable block, and proposers select the best bid. This concentrates MEV extraction but distributes the revenue more broadly.

Practical implications for developers:

Warning: If you are building a DEX or any contract where transaction ordering matters, assume that MEV bots will attempt to sandwich your users. Implement proper slippage protection, deadline parameters, and consider integrating with MEV-protection solutions like Flashbots Protect or MEV Blocker.

8.7 Gas Tokens: A Historical Curiosity

Gas tokens (GST2, CHI) were a clever but now-deprecated mechanism for "banking" gas. They exploited the SSTORE gas refund: users would mint gas tokens when gas was cheap (writing to storage), then burn them when gas was expensive (clearing storage and receiving the refund).

Why gas tokens no longer work:

EIP-3529 (London upgrade, August 2021) reduced the maximum gas refund from 50% to 20% of the total transaction gas. This made gas tokens uneconomical because the refund no longer covered the overhead of the token’s own logic.

Metric Pre-EIP-3529 Post-EIP-3529
Max refund 50% of gas used 20% of gas used
SSTORE clear refund 15,000 gas 4,800 gas
SELFDESTRUCT refund 24,000 gas 0 gas
Gas token viability Profitable Unprofitable

Gas tokens are now a historical artifact. If you encounter them in legacy code, they can be safely removed. The SELFDESTRUCT opcode itself is being phased out (EIP-6780 restricted it in the Dencun upgrade).

9.2 Transient Storage (EIP-1153)

EIP-1153, activated in the Dencun upgrade (March 2024), introduced TSTORE and TLOAD opcodes for transient storage — storage that persists only for the duration of a single transaction.

Why this matters for gas:

Operation Permanent Storage Transient Storage
Write 20,000 gas (new) / 5,000 gas (update) 100 gas
Read 2,100 gas (cold) / 100 gas (warm) 100 gas
Cleared after TX No (permanent) Yes (automatic)

Transient storage is ideal for:

  • Reentrancy guards — the classic _status variable now costs 100 gas instead of 5,000
  • Single-transaction callbacks — e.g., flash loan callbacks that need to pass data back
  • Temporary authorization — approve-and-use patterns within one transaction

Pro Tip: OpenZeppelin’s ReentrancyGuardTransient contract (available since v5.1) uses EIP-1153 transient storage automatically. If you are deploying to chains that support it (Ethereum, most L2s post-Dencun), prefer the transient variant.

9.3 PUSH0 (EIP-3855)

EIP-3855, activated with the Shanghai upgrade (April 2023), added the PUSH0 opcode — a dedicated instruction for pushing the value 0 onto the stack.

Before EIP-3855:

Pushing zero required PUSH1 0x00, which costs 3 gas and takes 2 bytes of bytecode.

After EIP-3855:

PUSH0 costs 2 gas and takes 1 byte of bytecode.

Practical impact:

This saves 1 gas per occurrence and 1 byte of deployment cost per occurrence. While small individually, zero is one of the most frequently pushed values in EVM bytecode. A typical contract might push zero hundreds of times, leading to measurable deployment cost savings.

To benefit: Set your Solidity compiler target to shanghai or later (or cancun / prague for the latest features):

10. Common Pitfalls and Debugging

10.1 Out-of-Gas Reverts

Symptom: Transaction reverts with "out of gas" error, all gas consumed.

Common causes:

  1. Infinite loops or unbounded iterations. A for loop iterating over a growing array can eventually exceed the block gas limit.

  2. Incorrect gas limit estimation. If you manually set the gas limit too low, even a valid transaction will fail. Always add a safety margin (typically 20-30%) above the estimated gas.

  3. State-dependent gas costs. A function that usually costs 200,000 gas might cost 2,000,000 gas when certain conditions are met (e.g., it triggers a token rebase or a complex fallback function).

Warning: eth_estimateGas simulates the transaction against the current state. If state changes between estimation and execution (e.g., another transaction modifies the same storage), the actual gas cost could be very different. This is especially common in DeFi where pool reserves change constantly.

10.2 Gas Estimation Failures

Symptom: eth_estimateGas throws an error before you even send the transaction.

What this means: The transaction would revert if executed. estimateGas runs a simulation and reports failure if the simulation reverts. The error message often contains the revert reason.

Debugging steps:

  1. Check the revert reason. Modern contracts use custom errors — decode the error data to understand why.

  1. Verify preconditions. Check balances, allowances, ownership, and contract state.

  2. Simulate with eth_call. This gives you the return data (or revert reason) without sending a real transaction.

  1. Check the sender’s balance. If the transaction sends value (msg.value), ensure the sender has enough native token to cover both the value and the gas cost.

10.5 Cross-Chain Gas Debugging

Symptom: Source chain transaction succeeds and gas is paid, but destination-side execution fails or nothing happens on the destination chain.

Debugging LayerZero cross-chain issues:

  1. Check the LayerZero Scan. Visit layerzeroscan.com and search for your source transaction hash. It shows the message status across chains.

  2. Insufficient destination gas. If lzReceive or lzCompose runs out of gas on the destination chain, the message may be stored in a "failed" state. You can retry it by calling lzReceive again with more gas (if the protocol supports retries).

  3. Verify enforced options. Ensure your setEnforcedOptions gas limits are sufficient. Common mistake: setting the lzCompose gas limit too low for a DEX swap that involves multiple hops.

  1. DVN verification delays. Sometimes the DVN verification takes longer than expected, especially on testnets. Wait at least 10-15 minutes before assuming failure.

  2. Executor balance. On testnets, the LayerZero Executor may run out of destination chain native tokens. This is a testnet-specific issue that does not occur on mainnet.
